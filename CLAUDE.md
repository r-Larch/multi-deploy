# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Multi-Deploy is a server-side tool (pure Bash) for hosting multiple Docker Compose apps on a single Ubuntu host behind one shared Caddy reverse proxy, with git-poll auto-deployment via systemd timers. There is no build step and no compiled language — the deliverable is the set of shell scripts in `bin/`, `setup.sh`, the systemd unit templates in `etc/`, and the Caddy stack in `caddy/`. `traefik/` is the v1 proxy, kept only so `app proxy cutover`/`rollback` can move a v1 server to Caddy (`docs/UPGRADING.md`).

It is installed to `/opt/multi-deploy` on the target server (the `INSTALL_DIR`). This repo *is* that directory's contents. Most logic assumes it runs as root on the server; you cannot meaningfully execute it on this Windows dev machine — edits here are pushed to GitHub and pulled onto the server by `setup.sh`.

## Architecture

The CLI is layered. `bin/app` is the user-facing dispatcher; it delegates to small single-purpose scripts, all of which `source bin/lib-app` for shared state and helpers:

- **`bin/app`** — command router (`create`, `deploy`, `list`, `logs`, `ci-logs`, `timers`, `detail`, etc.). Holds the interactive `create` wizard and read-only display commands.
- **`bin/lib-app`** — shared library. The contract everything depends on: `load_app <name>` sources `apps/<name>/app.env` and sets `NAME`, `APP_META_DIR`, `APP_REPO_DIR`, `APP_SSH_DIR`, `APP_COMPOSE_FILE`, and exports `GIT_SSH_COMMAND` (per-app SSH key with fallback to `/root/.ssh`). `build_compose_cmd` assembles the `compose_cmd` array (`docker compose --project-name <NAME> -f <APP_COMPOSE_FILE>`). `caddy_running` and `running_traefik` (names of running Traefik containers: compose project `traefik` or a `traefik` image) are the one proxy-state detection, used by `setup.sh` (which sources the installed `lib-app` after its sync), `app-proxy` and `app-migrate-proxy`. At source time it also exports `COMPOSE_PARALLEL_LIMIT` (default `1`) so compose builds/pulls one service at a time — set *before* `load_app`, so `app.env`, the systemd `EnvironmentFile`, or an inline `COMPOSE_PARALLEL_LIMIT=4 app deploy x` can raise it.
- **`bin/app-compose <name> ...args`** — loads context, ensures repo cloned, then `exec docker compose ...args`. The single choke point for every compose invocation.
- **`bin/app-git <name> <action>`** — all git operations (`status`, `fetch`, `pull`, `reset-hard`, `switch`) run inside `APP_REPO_DIR`. `status` emits the parseable line `branch=… commit=… ahead=N behind=N`.
- **`bin/app-proxy <validate|reload|status|logs|cutover|rollback|cleanup-traefik>`** — the single owner of every interaction with the shared Caddy proxy (container `multi-deploy-caddy`), exposed as `app proxy …`. `validate` runs multi-deploy's cross-app checks over `apps/*/global.caddy` and `apps/*/site.caddy` (a `global.caddy` holds only an `on_demand_tls` block and at most one app has one; at most one app has a catch-all site such as `https://` or `:443`, and it is the `on_demand_tls` owner; app snippets are named `(<app>-…)`; no `log` directive in `site.caddy`, since the root Caddyfile's `servers { trace }` logs every site), each refusal naming the apps, then `caddy validate` in the container, or in a throwaway container of the same image and files while Caddy is not running. `reload` = validate + `caddy reload`; on failure it prints Caddy's error and exits non-zero while Caddy keeps its running config. While Caddy is not running and Traefik is (a v1 server between the v2 install and the cutover), `reload` prints one line saying so and exits 0, so deploys and `app delete` keep working; with neither running it fails. `status` lists each app's hosts with the certificate expiry read from Caddy's storage (`/data/caddy/certificates/<issuer>/<host>/`, via host `openssl`). `logs` = `docker logs` of the container. `cutover`: preflight (Traefik runs, Caddy does not; every app with `traefik.http.routers.*` labels has a `site.caddy`; validate; every `reverse_proxy`/`forward_auth` upstream resolves on the web network from a throwaway curl container — curl exit 6 is "unresolved"; `caddy/.env` has `ACME_EMAIL`), then `docker compose down` in `traefik/`, `up -d` in `caddy/` (both through `proxy_compose`, so a `compose.override.yml` there applies), a check that only Caddy publishes :443, and per host of every `site.caddy` a poll from a throwaway container on the web network to Caddy's address (TLS trusted by `MD_PROXY_CA` or the system, status < 500, up to `MD_PROXY_HOST_TIMEOUT` s, default 120). Any failure runs the rollback and exits 1 naming the hosts. `rollback` = `down` in `caddy/`, `up -d` in `traefik/`, and every host checked through Traefik (`-k`, status < 500 and not Traefik's own `404 page not found`). `cleanup-traefik` refuses unless Caddy runs and Traefik does not; it removes the Traefik containers and `traefik/letsencrypt` (tarball in `backups/`, mode 600) and keeps the `traefik/` files. Throwaway containers carry `MD_RESOURCE_LABEL` when set (tests); their image is `MD_CHECK_IMAGE` (default `curlimages/curl:8.11.1`).
- **`bin/app-migrate-proxy <name> [--write|--drop-labels]`** — exposed as `app migrate-proxy`. Reads the `traefik.*` labels from `app-compose <name> config --format json` with jq (labels in `code/` count, `${VAR}`s are resolved, `$$` is un-escaped; nothing else of that config — it holds env values — is printed or written) and translates them: `Host(…) || Host(…)` → site addresses, upstream `<name>-<service>:<port>`, `flushinterval` → `import sse`, http routers that only redirect to https are dropped, a whole-host `redirectregex` (`^https?://<host>/(.*)` → `https://<to>/${1}`, to the apex or another domain, `service=noop@internal` allowed) → a `<host>[, http://<host>] { redir https://<to>{uri} [permanent] }` block with no `reverse_proxy`, `security-headers@file` → `import security-headers`, `compress` (excluding at most `text/event-stream`) → `import compress`, inline `headers` (`contentTypeNosniff`, `frameDeny`, `referrerPolicy`, `sts*`, custom request/response headers) → a `header { … }` block and `request_header`, `forwardauth` (`address`, `authResponseHeaders`, `trustForwardHeader`) → `forward_auth` (plus an INFO to check the auth endpoint), `loadbalancer.healthcheck.{path,interval,timeout,hostname}` → `health_*`; `tls`, `server.scheme=http`, `passhostheader=true` and `docker.network` are dropped. Everything else is a `TODO` line and exit 2 with nothing written. `--write` edits one file line by line with awk: `compose.server.yml` when it holds the labels, the app's own `compose.yml` for a static app that holds them, and `compose.server.yml` (alias only) when they live in `code/`, which is never edited. Known shape only: block-list `networks:` under the service, 2-space indent, LF; a missing service, `networks:` or top-level `web` network (or its `name:`) is added, any other shape is exit 2. The `traefik.*` labels stay, so a redeploy keeps Traefik routing the app until the cutover and a rollback finds it routable; every other byte stays too; the original goes to `<file>.traefik.bak`. An app whose service is aliased and has a `site.caddy` is reported as migrated. `--drop-labels` (refused unless Caddy runs and Traefik does not, and the app has a `site.caddy`) removes the `traefik.*` labels and their comment lines of every service from the edited file with the same awk editor (block-list `labels:` only), backup `<file>.labels.bak`; labels in `code/` are left to the app repo. Golden fixtures (anonymised production label shapes) live in `tests/fixtures/migrate/<app>/` (`expected.site.caddy`, `expected.<edited file>`, and `two-hosts/expected.dropped.compose.server.yml` for `--drop-labels`).
- **`bin/app-deploy <name> <update|deploy>`** — `deploy` = `build --pull` + `up -d --remove-orphans` + `app-proxy reload` (a refused proxy config fails the deploy); `update` delegates to `watch-and-deploy.sh`.
- **`bin/watch-and-deploy.sh`** — the unit of work systemd runs each minute. Clones repo if missing, logs to `apps/<name>/logs/<timestamp>.log` (tee'd, rotated after 7 days), calls `deploy.sh`.
- **`bin/deploy.sh`** — change-detection: only `build --pull` when the repo is *behind* origin (parsed from `app-git status`); when changed, runs `up -d --remove-orphans` and `app-proxy reload` (a reload failure fails the run).
- **`bin/docker-prune.sh`** — disk reclaim. Age-gated (`--days`, default 5) prune of unreferenced images, exited containers, buildx cache and unused networks; `flock`-serialised so the per-app timers don't stampede. Images labelled `multi-deploy.keep=true` are never pruned; `PRUNE_LABEL_SCOPE=<label>` (tests) limits every prune to that label and skips the build cache. Volumes only with explicit `--volumes`. Runs after every successful deploy (both `deploy.sh` and `app-deploy deploy`), plus a daily `docker-prune.timer` backstop; also exposed as `app prune`.

Key principle: git-status logic lives only in `app-git`, compose invocation lives only in `app-compose`/`build_compose_cmd`, and Caddy is touched only through `app-proxy`. When changing behavior, edit the single owner rather than duplicating — `app detail` and `deploy.sh` deliberately call back into `app-git`/`app-compose` to avoid drift.

### Per-app layout on the server (`/opt/multi-deploy/apps/<name>/`)

- `app.env` — generated config sourced by every command. Keys: `NAME`, `REPO`, `BRANCH`, `COMPOSE_FILE` (always `compose.yml`), optional `ENV_FILE` (path to a compose `--env-file`, relative to the app dir, e.g. `ENV_FILE=.env`; its variables are used for `${VAR}` substitution across the merged compose config — `COMPOSE_ENV_FILE` is the deprecated alias), optional `COMPOSE_PARALLEL_LIMIT` (overrides the serialised default of 1). **An empty/absent `REPO` means a "static app"** — no git, no timer; many commands branch on `[[ -z "${REPO:-}" ]]`.
- `compose.yml` — generated stack file using compose `include:` to merge the repo's compose file (`code/<file>`) with the server override.
- `compose.server.yml` — server-side override: attaches the chosen service to the external proxy network (`name: ${MD_WEB_NETWORK:-web}`; `lib-app` exports `MD_WEB_NETWORK` from `caddy/.env`) with the network alias `<name>-<service>`, keeping its `default` network. The repo's own compose stays untouched.
- `site.caddy` — the app's Caddy site blocks, imported by `caddy/Caddyfile` (mounted at `/etc/caddy/apps/<name>/`). `app create` writes it: host(s), `reverse_proxy <name>-<service>:<port>`, optional `{ import sse }` and `import security-headers`. This is where domain/routing config is hand-edited; apply with `app proxy reload`. `app delete` (behind a confirm) disables the timer, runs `app-compose <name> down` (named volumes stay; a failed down deletes nothing), removes the app directory and reloads; `app detail` prints it.
- `global.caddy` — optional, only an `on_demand_tls` block, for the one app that owns on-demand TLS.
- `code/` — the cloned app git repo.
- `.ssh/id_ed25519` — per-app deploy key (created on `app create` for SSH repos; the public key is printed to add as a deploy key). Falls back to `/root/.ssh` if absent.
- `logs/` — timestamped deploy logs, 7-day retention.

### Auto-deployment flow

`etc/systemd/multi-deploy@.timer` (every 1 min) → `multi-deploy@<name>.service` (oneshot, `EnvironmentFile=apps/%i/app.env`) → `watch-and-deploy.sh` → `deploy.sh`. Timers are toggled via `app timers <name> on|off`, which runs `systemctl enable/disable --now multi-deploy@<name>.timer`. The unit templates are installed to `/etc/systemd/system/` by `setup.sh`; editing the templates in `etc/` requires re-running setup (or copying + `daemon-reload`) on the server to take effect.

### Caddy

One Caddy container (`caddy/compose.yml`, container `multi-deploy-caddy`, image `${MD_CADDY_IMAGE:-caddy:2.11.9-alpine}`) owns ports 80/443 and the certificates (`caddy/data/`). It has no Docker socket: `caddy/Caddyfile` imports `caddy/snippets/*.caddy` (shared snippets `security-headers`, `sse`, `compress`, unprefixed) and `apps/*/global.caddy` + `apps/*/site.caddy`, and reaches each app through its alias `<name>-<service>` on the shared external network (`web`, or `MD_WEB_NETWORK`). `caddy/.env` (ACME_EMAIL, MD_WEB_NETWORK, MD_CADDY_IMAGE) and `caddy/data/` are user state, **excluded from setup.sh's rsync**. setup.sh creates the network and starts Caddy only where no Traefik runs; on a v1 server it installs the files and points to `docs/UPGRADING.md`. `traefik/` (`.env`, `dashboard_users`, `letsencrypt/` excluded from the rsync too) stays until a later release; nothing but `app proxy cutover|rollback|cleanup-traefik` uses it.

## Common tasks

Tests need Docker; everything Linux-specific runs in pinned containers (Git Bash on Windows): `bash tests/run.sh` (shellcheck of every script, unit tests in `tests/unit/` against stub `docker`/`systemctl`, Caddyfile validation) and `bash tests/e2e/run.sh` (setup.sh installs a snapshot of the checkout into a labelled volume, Caddy with `local_certs` and no host ports on the test network `md-test-web`; then a v1 install from `git archive 1.1.0` with Traefik is upgraded, cut over, rolled back, failed over on purpose and cleaned up; both scenarios source `tests/e2e/install.sh` for the install). `bash tests/e2e/run.sh --cms <repo>` runs only `tests/e2e/cms.sh` instead: the CMS repository's `HEAD` (`git archive`) becomes the app `mde2ecms` (never `cms`, a developer's own compose project) with the repository's kit `deploy/multi-deploy/cms/` (its `cms-` aliases and snippet renamed to the app's name in the copy) and a `compose.e2e.yml` in the include list (mailpit, `preview.test`, the builder's network/sandbox prefix/image named after the app, the run label on every container, built image, volume and network); after `app deploy` it checks that a forged `X-Forwarded-Host`/`-Proto` leaves the OpenID issuer alone, then runs the repository's `tests/e2e/smoke.mjs` runner (`CADDY_HOST`/`CADDY_ROOT_CA` pointing at the shared Caddy) on the test network plus the app's default network; `run.sh` then removes the project and asserts no `mde2ecms-*`/`mde2ecms_*` resource is left. Secrets (`GITHUB_PACKAGES_TOKEN`, `SIXLABORS_LICENSE_KEY`) come from the environment or the repository's `.env` and are written only to the app's `.env` in the test volume. Test resources carry `multi-deploy.test=<run>` and are removed on exit; `docker-prune.sh` is a no-op in the harness; never use the real `web` network or other compose projects.

Server-side install/update (idempotent; preserves `apps/`, `caddy/.env`, `caddy/data/`, `traefik/.env`, `dashboard_users`, `letsencrypt/`):

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/r-Larch/multi-deploy/refs/heads/master/setup.sh)"
```

End-to-end manual exercise on a server: `app create <name> <repo>` → check `apps/<name>/site.caddy` → `app deploy <name>` → `app logs <name>` / `app ci-logs <name>` (streams deploy logs, auto-rolls to newest file).

## Conventions when editing

- All scripts use `set -euo pipefail` and resolve `INSTALL_DIR` as `${INSTALL_DIR:-/opt/multi-deploy}`; reference sibling scripts as `"$INSTALL_DIR/bin/<name>"`, never by relative path.
- New `app` subcommands: add a `cmd_<x>` function, a `case` arm in `main()`, and a line in `usage()`.
- Keep the `COMPOSE_FILE=compose.yml` indirection — apps are addressed through the generated stack file, not the repo's compose directly.
- Interactive prompts go through `lib-app` helpers (`default_read`, `confirm`, `slugify`, `bold`, `red`); avoid raw `read`/`echo -e` for consistency. `default_read <prompt> <default> <VAR>` answers from `$VAR` when it is set, which makes `app create` scriptable (`APP_CREATE_BRANCH`, `APP_CREATE_SERVICE`, `APP_CREATE_HOST`, `APP_CREATE_PORT`, `APP_CREATE_SSE`, `APP_CREATE_HEADERS`; the e2e harness drives it this way).
- Comments state the present (no "used to", no narration of a change); remove dead code. Update README.md and this file in the same commit as the behaviour they describe.
- The repo is public: tests and docs use `.test` hosts and neutral names, never a production host, app or server.
- This is `master`-branch based (the install URL hard-codes `refs/heads/master`). The last v1 (Traefik) release is the tag `1.1.0`.
